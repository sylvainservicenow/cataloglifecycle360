## How to use this skill

There are three sources of reusable UI, checked in this order: the **local workspace** (UI already authored in this project), **packaged components** (bundled with AIUX), and **instance widgets** (`sys_aix_widget` records on the ServiceNow instance, not on disk). They are independent — the same capability may exist in more than one, and a local file does not mean the packaged or instance version is absent.

0. **Check the local workspace first.** Glob the project for UI the user already authored — widgets under `widgets/*/` (each has an `index.js`, often a `server-script.js`) and page-scoped components under `pages/**/components/*.js`. Read any file whose name or purpose plausibly matches the request; reuse it directly by its existing path/import. This is offline, free, and it is the user's own code — prefer it over rebuilding. Only when nothing local fits do you move on to the packaged/instance index below. **This workspace glob is for reusing local UI only. Do NOT use workspace or `node_modules` searches to decide whether a packaged component or an instance widget exists — those resolve from `@servicenow/karuna` and the instance regardless of what is on disk.**

   **Local wins over its own deployed copy.** A widget under `widgets/<tag>/` may also appear in the instance index as a row for this project's scope — it is the same widget, deployed. The local source is what the user is editing now; the instance copy is a deployment snapshot that is equal or older. When a local widget matches an index row by tag **and** that row's scope is this project's scope, use the local source and ignore that instance row: do not rank it, and do not fetch its source. Match scope against this project's scope from `now.config.json`, allowing for the 18-character scope-prefix truncation (e.g. project scope `x_snc_toast_consumer` matches index scope `x_snc_toast_consum`). This applies **only** to the exact same scope+tag identity — a widget with the same tag in a *different* scope is a different widget and stays a candidate.

1. Read every index row and rank all plausible candidates together. Components and widgets are independent deployed entries. Do not infer a relationship from similar tag names; if both overlap, evaluate their references separately.

2. Load every reference named in the candidate's `Reference` column. If it does not fit, try the next candidate. If nothing fits, say you checked the local workspace and the unified index and found no reusable match, then continue with the original request.

3. **If the candidate is a widget, run its fetch command before writing any code — every time.**

   ```bash
   node .claude/skills/ui-discovery/scripts/fetch-widget-source.js --key <scope>.<tag>
   ```

   A widget's API is not in the index and not in its reference. Neither carries its properties, events, slots or server-script contract; only its authored source does, and this command is the only thing that produces it.

   Run it even when you have used this widget before, even when its source is already in your context, and even if a cached copy exists somewhere on disk. The command asks the instance for the widget's current version and re-pulls when it changed, so it is the only way to know that what you remember is still true — a repeat run is one row and one column when nothing changed. **Never substitute a local file for it.** A widget edited or redeployed since the last fetch will happily accept markup built from the old API and do nothing at all: no error, no warning, working-looking code wired to an event name that no longer exists.

   This does not apply to components, whose reference is complete on its own.

4. **Check the candidate against the request before writing code.** Reading a reference tells you what the candidate *has*; it does not tell you what the request needs and the candidate lacks. List both: which parts of the user's request this component or widget satisfies, and which it does not. Base that on its source, not on its name or description — a widget that only dispatches `thing:approve` does not perform the approval, and a server script that never reads an input key silently ignores it.

   If a packaged component, controller, directive, context, or function does not behave as its reference describes, tell the user which statement did not hold and what you observed. Do not silently route around it; the reference is the owner's published contract, and a mismatch is something its owner needs to hear about.

   If anything is missing, **say so and stop for a decision**. Do not quietly ship the covered part as finished, and do not invent the missing behavior — you cannot edit a packaged component or a deployed widget, and routing around it (writing the missing logic into the page) changes who owns that logic, may duplicate what the owner ships next, and may bypass constraints the original enforces. Offer the real options: accept the partial capability, implement the rest in the page deliberately, choose a different candidate, build custom, or ask the owner to extend it. The failure this prevents is not an unfinished job — it is a partial result presented as a complete one.

5. **Add the import from the selected reference — every time, for both components and widgets.** The element does not render without it: an unimported custom element is silently inert (no error, no warning, just an empty tag), which is easy to mistake for "should just work" when a widget "resolves from the instance." That phrase describes where the imported *code* comes from, not whether an import statement is needed — it is, for both kinds of candidate. Do not add a package dependency: components are bundled with `@servicenow/karuna`, and a widget's import resolves from the instance at request time rather than from `node_modules`, but the `import` line itself is still required in the page/component that uses the element.

   **If a widget's custom element does not appear to render, the fix is almost always this missing import — check for it before considering anything else.** Never respond to a missing-import symptom by copying the widget's source into the local project (e.g. a new `widgets/<tag>/` directory): that turns a shared, instance-resolved widget into an untracked fork that immediately starts drifting from the original, which is the exact duplication this skill exists to prevent.

   **Controllers, directives, contexts, and functions are cataloged the same way.** Before writing a new `ReactiveController` (`addController`), a new Lit `directive()`, a new `createContext()`, or a helper that renders platform data (e.g. a form field from a field descriptor), check the `Kind` column for `controller` / `directive` / `context` / `function` rows first — these are versioned npm packages, not instance state, so treat them like component rows: read the reference, use the `## Import` line verbatim (a named import, e.g. `import {AMBController} from '...'`, not the side-effect import used for components), and don't re-implement functionality one of these already covers.

6. Mention what you selected and why. If the user asks to **insert**, **add**, or **use** UI and an exact reusable match exists, reuse it without stopping for confirmation. If the user explicitly asks to **create** or **build a new** widget or component and an exact reusable match exists, explain that match and ask whether to reuse it or create a new project-owned implementation — those are different ownership decisions. Do not silently substitute reuse for an explicit creation request, and do not create a duplicate without presenting the existing match. Capability gaps still require the decision in step 4.

**After a sync, the index you are reading is out of date.** You loaded this file when the skill activated; a successful `node .claude/skills/ui-discovery/scripts/sync-widgets.mjs` rewrites it on disk afterwards, so your copy still shows the widget table as it was *before* the sync — usually empty. The command prints the new widget rows in its output; rank those alongside the component rows, or re-read this file. Do not rank on the copy in your context and conclude no widget matched — that conclusion is indistinguishable from never having seen the widgets at all.

The widget snapshot does not update automatically. Attempt `node .claude/skills/ui-discovery/scripts/sync-widgets.mjs` once when a named widget is missing, the snapshot is more than a few days old, the project changes instances, or a widget was just deployed. If synchronization fails, continue with the existing widget snapshot and offline component catalog. Ask the user about instance or credential configuration only when they explicitly require a named installed widget; offer continuing without widget discovery as a non-blocking alternative.

**Confirm the index is current before relying on it.** When an index already exists and a widget looks like a match, run the read-only freshness check `node .claude/skills/ui-discovery/scripts/sync-widgets.mjs --check` first. It makes one tiny query and prints a single `ui-discovery: index …` line:

- `index current` — the snapshot still matches the instance; use it as-is, no re-sync.
- `index outdated` — a widget was added, edited, or removed since the last sync. Tell the user the widget index is outdated and you are refreshing it, then run `node .claude/skills/ui-discovery/scripts/sync-widgets.mjs` and reread this index.
- `index freshness-unknown` — the instance was unreachable. This is non-blocking: keep using the existing snapshot and the offline component catalog, and repeat only the short `reason:` line.

Do not silently trust a stale index: wiring a widget from an out-of-date snapshot produces subtly wrong props/events that are hard to debug later.
